# gc-lang v1.0.1 — generations that never wrap, and a panic-safe sweep

**A patch for two collector bugs.** A stale handle could become valid again after a slot had been reused `2^32` times, and a destructor that panicked during `collect` leaked its slot and left `len` wrong for the rest of the heap's life. Both are fixed. There is no public API change; upgrading is a `cargo update`.

The patch also corrects the documentation of `Tracer::mark`, which in 1.0.0 described cross-heap handles wrongly, and records the typing fix (and the other planned GC features) for 2.0.

## M60: stale handles came back after `2^32` reuses (ABA)

A `Gc<T>` is a slot index plus a 32-bit generation. Sweeping a slot advances its generation, so handles to the old occupant stop matching. 1.0.0 advanced it with `wrapping_add`, and the free list hands out the most recently freed slot first. An allocate/collect loop therefore reuses one slot every cycle, and after `2^32` cycles the generation is back where it started: a handle kept from the first cycle names the object allocated in the latest one. At the steady-state benchmark's rate (about 47 ns per three-object cycle on this machine) that is a few minutes of a hot loop, not a theoretical bound.

1.0.1 never wraps. A slot has exactly `2^32` generations, `0` through `u32::MAX`. When the occupant at `u32::MAX` is collected, the slot is **retired**: it stays empty, it is never returned to the free list, and nothing can ever be allocated into it again. No `(index, generation)` pair is issued twice, so a stale handle stays stale for the heap's whole lifetime.

### Capacity behaviour, exactly

- A retired slot keeps its place (and its memory) in the backing store and counts toward `capacity()`. The store still never shrinks.
- When a slot retires, the next allocation that finds no free slot appends a fresh one. A steady allocate/collect loop grows the store by **one slot per `2^32` reuses of a slot**, and not otherwise.
- Retired slots count toward the `u32::MAX + 1` slot-index ceiling. `GcError::CapacityExhausted` is returned when no slot is free and every index is occupied or retired. Retiring every index takes `2^32 × 2^32 = 2^64` allocations; if it ever happens, no collection can recover.

These rules are in the rustdoc for `Heap`, `alloc`, `try_alloc`, `capacity`, and `GcError`, and in [`docs/API.md#slot-lifetime`](https://github.com/jamesgober/gc-lang/blob/main/docs/API.md#slot-lifetime).

### How it is tested

Reaching the end of a generation range for real takes `2^32` reuses, so the tests use a `#[cfg(test)]`-only hook that moves a *free* slot's generation forward (never backwards). It does not exist in a normal build; the public API is unchanged.

- Unit tests: a slot retires at its last generation instead of wrapping; a retired slot rejects a handle of every generation through `get`, `get_mut`, `contains`, and as a root; a hot-slot loop run straight through retirement never issues a handle twice or revalidates one; three hot slots retiring cost exactly three fresh slots; a free slot at `u32::MAX` still takes its final occupant.
- A property test runs random sequences of allocations, collections (with stale handles mixed into the roots), and jumps of free slots to within a few generations of `u32::MAX`. After every step it checks against a model that every live handle resolves to its own object (each object carries a unique id), every dead handle resolves to `None`, no handle was ever issued twice, `len` is exact, and every empty slot is either on the free list or retired (no leaked slot). It passed at the default 256 cases and at 5,000.
- With the 1.0.0 `wrapping_add` sweep put back, the property and five of the unit tests fail.

## M61 (patch part): a panicking destructor leaked its slot and skewed `len`

1.0.0's sweep dropped each dead object first and did the slot's bookkeeping afterwards, and it subtracted the freed count from `len` only after the whole loop. If `T::drop` panicked, the unwind left the panicking slot empty but never on the free list (leaked for good), and `len` was too high by every object freed so far in that pass, permanently.

1.0.1 finishes each slot's bookkeeping before the destructor runs: take the object out of the slot, advance (or retire) the generation, put the slot on the free list, decrement the live count, and only then drop the object. That ordering is the drop guard. If the destructor panics, the panic propagates out of `collect`, and the heap it leaves is consistent:

- every slot swept up to and including the panicking one is fully reclaimed,
- every later slot still holds its object and still counts toward `len`,
- the next `collect` reclaims whatever the interrupted pass did not reach.

A panic in `Trace::trace` happens during mark, before anything is swept, so it never changed the heap. `collect` now also works on its pooled mark queue in place instead of moving it out and back, so a panic in user code no longer throws that allocation away.

`tests/panic_safety.rs` checks this through the public API with a type whose `Drop` panics (and one whose `trace` panics) under `catch_unwind`; the unit tests additionally check the free list and generations directly, including a panicking destructor in a slot's last generation. The public-API test fails on 1.0.0 (`len` reads 4 where 2 objects remain).

## M61 (docs): `Tracer::mark` accepts any handle

`Tracer::mark` is generic: it takes a `Gc<U>` for any `U`, and nothing checks that the handle belongs to the heap that is collecting. The collector reads every marked handle as a position in *that* heap. So a handle from another heap (of another type, or of the same type):

- **does not keep its own object alive.** An object in heap `B` referenced only from heap `A`'s objects survives `B`'s collections only if the runtime passes that handle to `B.collect` as a root.
- **may keep an unrelated object alive.** If its index and generation match a live object in `A`, that object is marked and traced though nothing in `A` refers to it. Never unsound, but it is over-retention.

1.0.0's rustdoc and `docs/API.md` said such a handle "is validated against its own heap when that heap collects". That was wrong; the docs now describe the real behaviour. Relatedly, a `Gc<T>` carries no heap identity, so `get` cannot detect a handle from another heap of the same `T`; that is now documented too. Behaviour is unchanged and pinned by `tests/cross_heap.rs`, which passes on both 1.0.0 and 1.0.1.

Typing `mark` to the collecting heap's handle type, and stamping handles with a heap id, are breaking changes. They are recorded for **2.0** in `dev/ROADMAP.md`, together with automatic collection triggers and weak handles.

## Performance

The sweep does the same work in a different order, plus one `checked_add` and one counter decrement per reclaimed slot. A new `collect_unreachable_tree` group (every object garbage, 10k / 100k / 1M) exercises that path; the existing `collect_reachable_tree` group is mark-heavy.

Same Windows x86_64 machine, Rust 1.95 stable, release build with fat LTO. 1.0.0 was built from the `v1.0.0` sources with the 1.0.1 bench file; the two bench binaries were run alternately, three times each. Best Criterion mean of the three runs:

| Bench | 1.0.0 | 1.0.1 |
|---|---:|---:|
| `collect_unreachable_tree/10000` | 79.2 µs | 77.7 µs |
| `collect_unreachable_tree/100000` | 797.7 µs | 864.6 µs |
| `collect_unreachable_tree/1000000` | 21.39 ms | 20.21 ms |
| `collect_reachable_tree/1000` | 10.86 µs | 10.59 µs |
| `collect_reachable_tree/10000` | 110.5 µs | 117.1 µs |
| `collect_reachable_tree/100000` | 1.191 ms | 1.123 ms |
| `steady_state_alloc_collect` | 46.73 ns | 45.97 ns |
| `alloc_reused_slot` (1,024 allocs) | 3.870 µs | 3.926 µs |
| `alloc_fresh_slot` (1,024 allocs) | 8.609 µs | 9.835 µs |
| `get_resolve` | 0.957 ns | 1.017 ns |

Differences go both ways and none is consistent across runs. `alloc_fresh_slot` and `get_resolve` run code 1.0.1 did not change, and they differ by up to 14%, which is the noise floor here. Read the table as "no measurable change". The README's performance table still shows the 1.0.0 WSL2 figures.

## Breaking changes

**None.** The public surface is identical to 1.0.0. Two behaviours change, both from wrong to right: a stale handle no longer revalidates after `2^32` reuses of its slot (a retired slot instead costs one fresh slot), and a panicking destructor no longer leaks its slot or corrupts `len`.
